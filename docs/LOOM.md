# Loom 엔진 기술 문서

Loom은 Omniweave의 문서 코어입니다. 한 문장으로 요약하면:

> **모든 불변 조각에 내용 주소를 매기고, 화면·저장·히스토리를 그 주소의 함수로 만든다.**

이 문서는 코드에 있는 그대로를 설명합니다. 함수·파일 이름은 실제 소스 기준이며, 계획은 **(로드맵)** 으로 표시합니다.

| 파일 | 역할 |
|---|---|
| `src/core/hash.ts` | `hashBytes`, `hashString` — 64비트 내용 해시 |
| `src/core/types.ts` | 씬 그래프 타입, `TILE = 256` |
| `src/core/loom.ts` | `makeTile`, `nodeHash`, `regionKey`, `weaveKey`, `dehydrate`/`hydrate`, `documentRoot` |
| `src/core/assets.ts` | 내용 주소 자산 저장소 `putBlob`/`getBlob` |
| `src/core/store.ts` | 불변 문서 + 히스토리 (`commit`, `undo`, `redo`, 제스처) |
| `src/render/weave.ts` | `WeaveCache` — 화면 타일 LRU 렌더러 |
| `src/render/brush.ts` | 브러시: 획을 닿은 타일에만 합성해 새 타일 스레드 생성 |
| `src/io/omw.ts` | `.omw` 패키저 `packOmw`/`unpackOmw` |
| `src/io/journal.ts` | Shuttle 저널 (IndexedDB 증분 자동 저장) |

---

## 1. Thread — 내용 주소 조각

### 1.1 해시 (`src/core/hash.ts`)

`hashBytes(bytes, seed)`는 32비트 레인 두 개(`h1`, `h2`)를 `Math.imul` 곱셈 혼합과 회전으로 섞는 cyrb 계열의 **비암호학적** 해시입니다.

- 입력이 4바이트 정렬이면 `Uint32Array` 뷰로 **워드 단위**로 읽습니다(정렬되지 않은 뷰는 바이트를 조립해 같은 결과를 냄 — 테스트 `hash is stable and content-sensitive`).
- 마지막에 길이를 섞고 두 레인을 교차 혼합해 16자리 16진수(64비트) 문자열을 돌려줍니다.
- `hashString`은 UTF-8로 인코딩한 뒤 `hashBytes`를 부릅니다.

측정: 256×256 RGBA 타일(256 KiB) 하나에 평균 약 0.24–0.25 ms (Node, Intel Core Ultra 5 125H). 재현은 `npm run bench`.

### 1.2 무엇이 Thread인가

| 조각 | 주소 계산 | 위치 |
|---|---|---|
| 픽셀 타일 | `makeTile(data)` → `{ hash: hashBytes(data), data }` | `loom.ts` |
| 씬 노드 | `nodeHash(n)` = 픽셀 버퍼를 뺀 `JSON.stringify(n)`의 해시, **객체 정체성으로 `WeakMap` 메모** | `loom.ts` |
| 래스터 속성 | `rasterPropsHash(n)` = 타일 맵을 뺀 노드 속성의 해시 (메모) | `loom.ts` |
| 자산 | `putBlob(bytes)` → `hashBytes(bytes)`, 같은 해시면 한 번만 보관 | `assets.ts` |
| 문서 전체 | `documentRoot(doc)` = 페이지 속성 해시 + 노드 해시 + 자산 표 해시를 이은 해시 | `loom.ts` |

**불변성 전제.** 문서는 immer `produce`로만 바뀌므로, 바뀌지 않은 페이지·노드·타일은 이전 버전과 **같은 객체**를 공유합니다(구조적 공유). 그래서 "객체 정체성 = 내용 정체성"이 성립하고, `nodeHash`를 객체별로 한 번만 계산해도 됩니다.

### 1.3 희소 타일

래스터 노드는 `tiles: Record<"tx_ty", PixelTile>`인 희소 맵입니다. 브러시(`render/brush.ts`)는 획이 끝나면 마스크를 **닿은 타일에만** 합성해 새 타일 스레드를 만들고, `isBlank`(모든 알파가 0)인 타일은 맵에서 뺍니다. 닿지 않은 타일은 객체와 주소가 그대로 유지됩니다.

## 2. Weave Cache — 무효화 없는 화면 캐시

### 2.1 키 (`regionKey`, `weaveKey` in `src/core/loom.ts`)

화면은 256 **장치 픽셀** 크기의 타일 격자로 덮입니다. 각 화면 타일의 키는:

```text
weaveKey = hashString( 페이지 배경 | 페이지 크기 | 배율 | 영역 좌표
                       | regionKey(마스터 노드들) | regionKey(페이지 노드들) )
```

`regionKey(node, region)`:

- 보이지 않거나(`visible = false`) 경계 상자가 영역과 겹치지 않으면 → 기여 없음.
- **래스터 노드**: `rasterPropsHash(node)` + **그 영역 아래에 있는 타일들의 해시만** (`rasterTileKeysIn`). 그래서 브러시로 타일 하나를 바꾸면 그 타일과 겹치는 화면 타일의 키만 바뀝니다.
- **그 밖의 노드**(벡터·텍스트·이미지·PDF): `nodeHash(node)` 전체.

테스트 `weave key changes only for regions whose threads changed`가 이 성질을 확인합니다.

### 2.2 렌더 (`WeaveCache.render` in `src/render/weave.ts`)

1. 확대 배율을 **4분의 1 옥타브** 단위로 양자화합니다(`q = 2^(round(log2(zoom·dpr)·4)/4)`). 조금씩 확대해도 같은 키를 재사용하고, 화면에 옮길 때 보간합니다.
2. 보이는 페이지 영역에 걸친 각 화면 타일에 대해 `weaveKey`를 계산합니다.
3. LRU에 키가 있으면 그대로 화면에 복사(적중), 없으면 그 타일에 닿는 노드만 256×256 캔버스에 그린 뒤 LRU에 넣습니다(실패).
4. 이미지·PDF 비트맵 같은 비동기 자원이 아직 준비되지 않아 **불완전하게 그려진 타일은 캐시에 넣지 않습니다**(`env.incomplete`). 자원이 도착하면 다시 그립니다.
5. LRU 상한은 기본 1600타일(타일당 256 KiB, 최악 약 400 MB). 밀려난 캔버스는 풀(pool)로 돌아가 재사용됩니다.

### 2.3 왜 "오래된 픽셀"이 구조적으로 불가능한가

일반적인 캐시는 "무엇이 바뀌었는지"를 추적하는 dirty 플래그와 무효화 코드가 필요하고, 그 코드의 빈틈이 *지웠는데 화면에 남아 있는* 버그가 됩니다.
Weave Cache에는 그런 코드가 **아예 없습니다**. 타일 내용은 키의 순수 함수이고, 키는 그 영역에 영향을 주는 모든 입력의 주소로 만들어집니다. 내용이 바뀌면 키가 바뀌어 다른 칸을 찾게 되므로, 오래된 칸은 그저 다시 쓰이지 않다가 LRU에서 밀려납니다.

부수 효과로, **실행 취소·다시 실행·페이지 왕복** 시 예전 문서의 키가 다시 나타나면 이전에 그린 타일이 그대로 적중합니다.

> 전제: 렌더 결과가 키에 포함된 입력에만 의존해야 합니다. 키에 넣지 않은 외부 상태(예: 문서 밖 전역 설정)에 따라 그림이 달라지는 기능을 추가할 때는 그 상태를 키에 넣어야 합니다. 비동기 자원은 위 4번의 "불완전 타일은 캐시하지 않음" 규칙으로 처리합니다.

### 2.4 측정

1920×1080 페이지(화면 타일 40개, 래스터 1 + 벡터 20 + 텍스트 10 노드)에서 한 프레임 전체 키 계산: 평균 약 0.36–0.43 ms, 브러시 타일 하나가 바뀐 직후(새 노드 객체 포함) 약 0.44 ms. 렌더(캔버스 그리기)는 브라우저가 필요해 벤치에 포함하지 않았습니다. 앱 상태 표시줄의 Loom 미터가 실제 적중률과 렌더 시간을 보여 줍니다.

## 3. 히스토리 — 참조 교체

`src/core/store.ts`의 상태는 `doc`(현재 불변 문서), `past[]`, `future[]`입니다.

- `commit(label, recipe)`: immer로 다음 문서를 만들고, 이전 문서 **참조**를 `past`에 넣습니다(최대 300개).
- `undo()`: `past`의 마지막 문서를 `doc`으로, 현재 문서를 `future`로 옮깁니다. `redo()`는 반대.
- **제스처**(`beginGesture` → `updateGesture` 반복 → `endGesture`): 드래그·스크럽·색 끌기 동안 매 프레임 문서를 바꾸지만 히스토리에는 **한 단계**만 남깁니다.

픽셀 데이터를 복사하지 않으므로 실행 취소 비용은 문서 크기와 무관합니다. 측정: 작은 문서와 합성 4K 문서(타일 참조 205개) 모두 undo+redo 한 쌍이 평균 0.1–0.2 ms 수준이었고, 같은 4K 문서를 `structuredClone`으로 깊은 복사하는 데는 24–28 ms가 걸렸습니다(복사 방식 히스토리의 대조값).

정확히 말하면 `past`/`future` 배열 자체는 `slice`로 새로 만들어지므로 히스토리 길이(최대 300)에 비례하는 **포인터 복사**가 있습니다. "O(1)"은 문서 크기에 대한 말입니다.

히스토리의 메모리는 구조적 공유 덕분에 **바뀐 부분만큼만** 늘어납니다. 브러시 한 획이 타일 3개를 바꿨다면 그 버전이 새로 가지는 픽셀은 타일 3개분입니다.

## 4. Shuttle — 저장과 복구

### 4.1 dehydrate / hydrate (`src/core/loom.ts`)

- `dehydrate(doc)`: 래스터 타일 객체를 **해시 문자열**로 바꾼 평범한 그래프와, `해시 → 픽셀` 맵을 돌려줍니다. 같은 타일이 여러 곳에 있어도 맵에는 한 번만 들어갑니다(**중복 제거**).
- `hydrate(graph, getTile)`: 해시마다 픽셀을 가져와 **길이와 해시를 다시 검증**합니다. 없으면 `missingTiles`, 맞지 않으면 `corruptTiles`를 세고 그 타일만 건너뜁니다. 같은 해시는 한 번만 검증합니다.

### 4.2 `.omw` 패키지 (`src/io/omw.ts`)

`packOmw`는 `dehydrate` 결과를 CBOR(`scene_graph.cbor`)로, 고유 타일을 `rasters/<hash>.raw`로, 자산을 `assets/<hash>.<ext>`로 zip에 넣고, `manifest.json`에 `documentRoot`를 적습니다. 이미 압축된 형식(PNG/JPEG/WebP/GIF/WOFF2)은 다시 압축하지 않습니다.

> 2026-11-12부터 기본 저장은 **container 2**입니다: 그래프는 `scene_graph2.cbor`, 타일은 무손실 PNG `rasters/<hash>.png`, 손대지 않은 PSD 레이어 타일은 원본 PSD에서 다시 만드는 목록 `rasters/derived.json`, 히스토리는 장면 그래프의 노드를 되풀이하지 않습니다. 읽기는 container 1·2 모두. 자세한 내용·측정은 `docs/design/FILE_SIZE.md`.

`unpackOmw`는 `mimetype`을 확인하고, 타일과 자산을 모두 해시 검증한 뒤, 다시 계산한 `documentRoot`가 manifest와 같은지(`rootMatches`) 보고합니다. 손상된 타일이 있어도 **나머지 문서는 열립니다** (테스트 `detects a corrupted tile and still loads`).

측정(합성 4K 문서, 타일 참조 205개): 고유 타일 42개로 타일 데이터 79.5% 제거, 원시 RGBA 51.3 MiB → `.omw` 1.43 MiB, 저장 약 760–780 ms(대부분 zip 압축), 열기(전체 해시 검증 포함) 약 0.1–0.3 s.

### 4.3 저널 (`src/io/journal.ts`)

- 앱은 마지막 변경 1.5초 뒤, 저장하지 않은 편집이 있을 때 `journalSave`를 부릅니다(`src/ui/App.tsx`).
- `journalSave`는 IndexedDB `threads` 저장소에 **이번 세션에서 아직 쓰지 않은** 타일·자산만 쓰고(`written` 집합), `roots`에 최신 그래프 하나(`latest`)를 덮어씁니다. 그래서 브러시 한 획 뒤 자동 저장은 "새 타일 몇 개 + 작은 그래프"입니다.
- 다음 실행 때 `journalPeek`로 복구할 내용이 있는지 보고, `journalRestore`가 그래프와 조각을 읽어 `hydrate`합니다.

## 5. 한글 조판 (`src/core/text.ts`)

Loom의 일부는 아니지만 같은 "하나의 파이프라인" 원칙을 따릅니다. Word·HWPX·슬라이드 텍스트가 모두 같은 `layoutText`를 씁니다.

- **그래핌 단위 줄바꿈**: `Intl.Segmenter`로 글자 경계를 나눠, 한글 음절이나 결합 자모가 줄 끝에서 쪼개지지 않습니다.
- **`keep-all`**: 어절(띄어쓰기 단위) 사이에서만 줄을 바꿉니다. 한 어절이 줄보다 길면 그래핌 단위로 나눕니다.
- 측정 결과는 캐시합니다(최대 5만 항목).

## 6. 한계와 주의 (정직하게)

| 항목 | 내용 |
|---|---|
| **해시는 보안용이 아님** | 64비트 비암호학적 해시입니다. 우연한 충돌 확률은 매우 낮지만(조각 100만 개일 때 생일 문제 근사로 약 3×10⁻⁸), **의도적으로 충돌을 만드는 공격은 막지 못합니다.** 무결성 검증은 "저장 매체 손상·전송 오류 감지"용이며 변조 방지나 서명이 아닙니다. 해시의 통계적 품질은 공식 테스트 도구(SMHasher 등)로 아직 평가하지 않았습니다. |
| 충돌 시 영향 | 서로 다른 두 타일이 같은 주소를 가지면 저장 시 하나로 합쳐지고, 화면 캐시가 다른 타일 그림을 재사용할 수 있습니다. |
| `nodeHash`의 비용 | 노드를 `JSON.stringify`해서 해시합니다. 객체별 메모로 한 번만 계산하지만, 매우 긴 텍스트 노드는 바뀔 때마다 전체를 다시 직렬화합니다. 키 순서가 같은 객체 생성 경로에 의존합니다. |
| 키 계산은 노드 수에 비례 | 화면 타일마다 모든 노드의 경계 상자를 확인합니다(O(화면 타일 × 노드)). 노드가 수천 개인 페이지에서는 공간 색인이 필요합니다 **(로드맵)**. |
| 보수적인 경계 상자 | 벡터·텍스트 노드는 경계 상자가 겹치면 실제로 칠하지 않아도 키에 기여합니다. 정확성에는 문제없고, 불필요한 다시 그리기가 조금 생길 수 있습니다. |
| 렌더러 | 현재 Canvas 2D입니다. WebGPU 렌더러와 Rust/WASM 코어는 **(로드맵)** 입니다. |
| 저널 가비지 | IndexedDB `threads`에 쓴 조각은 `journalClear` 전까지 지우지 않습니다(참조 계수·GC 없음). 오래 작업하면 저장소가 커질 수 있습니다. 루트는 `latest` 하나뿐이라 여러 문서의 동시 복구는 지원하지 않습니다. |
| 손상 타일 | 검증에 실패한 타일은 건너뛰므로 그 자리는 투명하게 보입니다. 복원하지는 않습니다. |
| 메모리 상한 | Weave Cache 최대 1600타일(최악 약 400 MB). 저사양 기기용 조정은 아직 없습니다. |

## 7. 벤치마크 재현

```bash
npm run bench     # = vitest bench --run, bench/loom.bench.ts
node -p "os.cpus()[0].model"
```

벤치는 결정적 의사 난수로 합성 문서를 만들며, 크기·중복 제거 수치는 실행할 때 먼저 출력됩니다. 시간 값은 기기와 부하에 따라 달라집니다.

## 8. 편집 보조 — 자유 변형·자르기·안내선·페이지 정리

모두 순수 함수(`src/core/transform.ts`·`crop.ts`·`snap.ts`·`align.ts`·`pages.ts`·`units.ts`)와 얇은 UI로 나뉩니다. 문서 변경은 전부 `store.commit`이나 제스처(끌기 1번 = 실행 취소 1단계)로 들어가 히스토리·.omw 저장에 그대로 남습니다.

**자유 변형 (`core/transform.ts`)**
- 선택 상자에 손잡이 8개(여러 개 선택은 모서리 4개). 모서리 = 두 방향, 변 = 한 방향, **Alt = 가운데 기준**, 모서리 바깥 = 회전(**Shift = 15°**, 스냅이 켜져 있으면 15° 근처 4° 안에서 끌림).
- 비율: 이미지·래스터(PSD 레이어)·PDF·미디어는 **기본 비율 고정, Shift로 해제**(포토샵 2026), 벡터·텍스트·표는 반대로 **Shift = 비율 고정**. 여러 개는 항상 비율 고정.
- 텍스트 상자: 모든 손잡이가 **상자 너비**만 바꿉니다(글이 다시 흐르고 높이는 내용이 정함). **Ctrl+모서리 = 글자까지 비례 확대**.
- 비균일 크기는 `Transform.scaleY?`(없으면 `scale`과 같음 → 기존 파일·해시 불변). 음수 = 뒤집기. geom·draw·pdfVector(`cm`)·SVG·PSD 저장(리샘플 경로)이 모두 따릅니다. 이미지·미디어는 `width/height`를 바꾸고, 나머지는 `scale/scaleY`.
- 누르기 우선순위(`pointerTarget`): 손잡이 위 → 손잡이 / 회전 영역은 **그 자리에 다른 개체 픽셀이 없을 때만** / 그 외에는 기존 픽셀 히트 테스트 그대로(클릭한 픽셀의 레이어가 선택되고 바로 이동) / 선택 상자 안 빈 곳 → 선택 이동 / 바깥 → 영역 선택.
- Ctrl+T: 변형 세션 — Enter 확정, Esc는 세션 동안의 단계를 모두 실행 취소.

**자르기 (`core/crop.ts`, 비파괴)** — 이미지·래스터 레이어·PDF 페이지에 선택 필드 `crop?: {x,y,w,h}`(노드 좌표). 원본 픽셀·PDF 연산자는 그대로 두고 보이는 영역만 바뀝니다. 화면(draw clip), 경계 상자·히트, 벡터 PDF(클립 경로 — 원본 이미지/쪽은 통째로 들어감), SVG(clipPath), PSD 저장(잘린 레이어는 리샘플 경로로 보이는 영역만 기록)이 따릅니다. 전체를 보이게 하면 필드가 지워집니다.

**페이지 90° 회전 (`rotatePageInPlace`)** — 모든 페이지 종류에 같은 규칙: 폭·높이를 바꾸고 모든 개체(가져온 PDF 쪽도 하나의 개체)를 페이지 원점 기준으로 함께 돌립니다. 리샘플이 없어 PDF 쪽은 벡터 원본 그대로(내보낼 때 회전 행렬로 embed), 안내선도 함께 돕니다. 마스터 개체·애니메이션 경로는 돌리지 않습니다.

**안내선** — 페이지별 `Page.guides?: {x?: number[]; y?: number[]}`(페이지 px, x = 세로선). 마스터의 안내선은 연결된 슬라이드에 점선으로 보이고 스냅에 쓰이지만 마스터에서만 고칩니다. 눈금자 단위는 문서·PDF = mm, 그 밖 = px(눈금자 모서리에서 변경), 격자 기본값은 문서·PDF 10 mm/2칸, 슬라이드 40 px/4칸, 디자인 80 px/4칸.

**스냅** — 제스처를 시작할 때 후보선(격자·안내선·페이지 가장자리/중앙·다른 개체 가장자리/중심)을 한 번 정렬하고, 움직일 때마다 이진 탐색으로 찾습니다. 같은 간격은 행·열 버킷(256 px)으로 이웃만 봅니다. 화면에서 6 px(줌 무관), Alt를 누르는 동안 꺼짐. 개체 1만 개: 색인 약 50 ms, 이동 1회 약 0.1 ms(단독 실행 기준). 화면 근처 개체만(최대 4000개) 후보로 넣습니다.
