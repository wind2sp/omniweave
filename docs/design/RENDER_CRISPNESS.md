# 화면 선명도 (Render crispness)

2026-11-13, 그리기 품질 부서. 제품 검토 의견: "아트보드의 개체나 글상자가 맥처럼 약간 번져 보인다 — 한글·워드·일러스트처럼 또렷해야 한다."
합격 기준 두 갈래: (1) 글자 — 같은 확대율·같은 글꼴에서 Windows 앱(ClearType) 글자와 나란히 놓아 번짐이 눈에 띄지 않을 것,
(2) 선·도형·선택 표시 — 1px 선은 정확히 1장치픽셀, 선택 상자·손잡이·안내선·경로 미리보기가 100/125/150 % 배율에서 번지지 않을 것.

원칙: **화면 표시 경로만** 바꾼다. 모델 좌표·조판·내보내기(PDF/PNG/썸네일: `paintPage`)는 그대로다.

## 1. 측정 (짐작 없이)

도구: 개발 서버 + Claude Browser 창(Chrome 156, WebView2와 같은 Blink/Skia). 캔버스 픽셀을 직접 읽어 비교했다.
dpr 1은 실제 화면, dpr 1.25 / 1.5는 `window.devicePixelRatio`를 바꿔 백버퍼를 그 배율로 그리게 한 에뮬레이션(그려진 장치 픽셀 그대로를 측정).
지표: **acutance** = 밝기 기울기 합 / 잉크 합(클수록 가장자리 또렷), **ink px** = 배경보다 어두운 픽셀 수(같은 글자에서 적을수록 덜 번짐),
**LCD px** = R·G·B가 다른 픽셀 수(ClearType식 서브픽셀 AA 여부), **overlay partial** = 선택 표시 영역에서 반쯤 칠해진(알파 1–254) 픽셀 비율(0에 가까울수록 1px 정확).

### 원인 A — 글자가 회색조 AA로만 그려짐 (가장 큰 원인, 모든 배율)
- 쪽은 256장치픽셀 타일(`WeaveCache`)에 그려 두었다가 화면에 붙인다. 타일은 **투명** `OffscreenCanvas`였다.
- 실험: 같은 글자(맑은 고딕 13px)를 그려 R·G·B 차이를 셈.
  투명 캔버스 / OffscreenCanvas → LCD px **0** (회색조), `getContext('2d', {alpha:false})` → LCD px **400**, 잉크 픽셀 472 → 391.
  변환(×0.63, ×1.25, 회전)·clip·globalAlpha·multiply에서도 불투명이면 LCD 유지.
- 즉 DOM 글자·워드·한글은 ClearType(서브픽셀)인데 오메 캔버스 글자만 회색조 → "맥처럼 부드럽게 번진" 느낌의 정체.
- 기준선: Skia가 가로쓰기 기준선 y를 장치 정수로 이미 반올림한다(20.3 → 20, 20.5 → 21 측정). 따로 맞출 필요 없음 → 줄마다 흔들림 문제도 없음.

### 원인 B — 확대율 양자화 후 재표본 (63 %·150 %, 그리고 125 % 화면의 100 %)
- 타일 배율을 1/4옥타브(2^0.25 = 1.19배 간격)로 반올림해 그린 뒤 화면 크기로 늘이거나 줄여 붙였다.
  63 % → 0.595로 그려 ×1.06 확대, 150 % → 1.414로 그려 ×1.06, **125 % 화면에서 100 %** → 1.19로 그려 ×1.05 축소.
  dpr 1·100 %만 우연히 1:1이었다. 쌍선형 재표본이라 모든 글자·선이 반 픽셀씩 번졌다.

### 원인 C — 캔버스 백버퍼와 화면 픽셀의 어긋남 (125 %·150 % 화면)
- `cv.width = Math.round(clientWidth × dpr)`: `clientWidth`는 정수로 잘린 CSS 폭이라 125 %에서 백버퍼가 실제 표시 장치 픽셀과 0.25–1 px 어긋나고,
  합성기가 캔버스 전체를 다시 늘여 그렸다(전체가 미세하게 번짐). 눈금자 캔버스도 같은 계산.

### 원인 D — 선택 표시·안내선이 장치 픽셀 사이에 걸침
- 오버레이는 CSS px 좌표로 `Math.round(x)+0.5`에 맞췄는데, 이는 dpr 1에서만 픽셀 중앙이다. 125 %에서는 1 CSS px = 1.25장치px 선이 두 픽셀에 걸쳐 번졌다.
- 선택 윤곽선 굵기 1.25 CSS px, 앵커 사각형 좌표 미반올림, 마퀴·도형 미리보기·자르기 삼분선 미맞춤.
- 측정(overlay partial, 표 선택 영역): dpr 1 0.57→**0.05**, dpr 1.25 0.71→**0.04**, dpr 1.5 0.54→**0.04** (남은 몇 %는 의도된 반투명 여백선·점선 끝).

### 원인 E — 표 괘선이 1모델px 그대로 (확대율에 따라 0.63장치px·1.5장치px로 번짐)
- 워드·한글은 괘선을 최소 1장치픽셀로 픽셀 격자에 맞춰 보인다. 오메는 모델 굵기 그대로 그려 63 %에선 흐릿한 회색, 150 %에선 2픽셀에 걸친 띠.

## 4. 남은 한계

1. **글자 입력 중(리치 편집기)**: 편집 중인 글상자는 DOM `contenteditable`을 `transform: scale(zoom)` + 반투명 배경(`rgba(255,255,255,.85)`)으로 겹쳐 보인다.
   실험: Chrome은 transform이 걸리거나 배경이 반투명인 DOM 글자를 회색조로 그린다(LCD px 0). 글꼴 크기로 배율을 주고 불투명 배경일 때만 LCD(173 px).
   그래서 입력 중에는 캔버스(후)보다 약간 흐리다. `RichTextEditor.tsx`는 문서 핵심 부서 영역이라 손대지 않음 — 권고: 배경을 쪽 색(불투명)으로,
   배율은 transform 대신 글꼴 크기·폭에 반영(줄 나눔이 캔버스 조판과 같은지 확인 필요).
2. **워드·한글 창 직접 캡처 비교는 하지 않음**: 사용자 화면의 다른 앱을 조작해야 해서. 대신 같은 DirectWrite/ClearType 경로인 Chrome DOM 글자를 기준으로 비교.
   워드·한글은 글꼴 힌팅(격자 맞춤)을 더 강하게 써서 9 pt 이하 작은 글자에서는 획이 더 굵고 정수 픽셀에 붙어 보일 수 있다 — 캔버스는 Skia 기본(가로 서브픽셀 위치, 약한 힌팅).
3. **실제 125 %·150 % 모니터 확인**: 이 PC 화면이 100 %라 1.25/1.5는 백버퍼 에뮬레이션으로 측정했다. `devicePixelContentBoxSize` 1:1 보장은 표준 동작이지만
   실제 고배율 모니터(Tauri/WebView2)에서 한 번 눈으로 확인 필요.
4. **도형 윤곽선·벡터 경로**는 모델 굵기 그대로(일러스트레이터의 기본 "픽셀 미리보기 끔"과 같음). 표 괘선만 워드·한글처럼 맞춤.
5. 연속 확대 중(160 ms 동안)에는 예전처럼 재표본 타일이라 약간 부드럽고, LCD 무늬가 ±6 % 늘어난 채 보일 수 있다. 멈추면 곧바로 또렷해진다.
6. 투명 배경 쪽(래스터 문서 등)은 회색조 AA 그대로(LCD는 불투명 배경 위에서만 올바름).
7. 왼쪽 쪽 썸네일(`src/ui/shell/Thumbs.tsx`, 문서 화면 부서)은 CSS 높이 109.125px에 백버퍼 109px — 미세 재표본. 이번 범위 밖.

## 5. PDF·AI 쪽 (2026-11-24, 0.2.2 사용자 보고: "AI가 기본 화면에서 뿌옇고 깨진 것처럼 저해상도, 확대하면 나아짐")

원인
- **F — 대역(bucket) 그림을 늘이고 줄임**: 화면의 PDF 쪽(0.2.2의 AI 포함)은 pdf.js가 0.5·1·2·4배 중 하나로 그린 그림을 확대율에 맞춰 늘이거나 줄여 붙였다.
  맞춤 배율(0.48–0.74)·125 %·150 % 화면에서는 항상 재표본(쌍선형) — 글자 획이 번짐. 4배 위로는 더 커지지 않음.
- **G — 썸네일 대역 그림이 타일에 굳음**: 정확한 그림이 아직 없을 때 이미 그려 둔 아무 그림(쪽 썸네일·최근 파일용 작은 그림)을 대신 썼는데,
  화면용(`exact=false`)에는 '미완성' 표시가 없어 그 타일이 캐시에 남았다. 제대로 된 그림이 끝나도 같은 확대율에서는 캐시가 맞아 다시 그리지 않음
  → 작은 그림을 크게 늘린 계단 모양이 확대율을 바꿀 때까지 남음("확대하면 나아짐"과 일치). 썸네일이 먼저 끝나는 경쟁이라 늘 재현되지는 않음.
- (측정 함정) Playwright `device_scale_factor`(CDP 에뮬레이션)는 `devicePixelContentBoxSize`를 CSS px로 줘서 캔버스 백버퍼가 1배로 잡힌다.
  실제 고배율과 같게 보려면 `--force-device-scale-factor=<배율>`로 띄워야 한다(이때 백버퍼 = CSS × 배율 확인).

고침 (`src/io/pdf.ts` `pdfScreenBitmap`, `src/render/draw.ts` `drawPdfScreen`, 스위치 `crisp.pdfScreen`)
- 화면 타일의 PDF 쪽은 (확대율 × 장치 픽셀 비율 × 개체 배율)을 캔버스 변환에서 읽어 pdf.js로 **그 배율 그대로** 그리고, 장치 정수 위치에 1:1로 놓음
  (Acrobat·Illustrator처럼 벡터·글자를 화면 해상도로). 확대 제스처 중에는 weave의 1/4옥타브 타일 배율을 따르고, 멈추면 정확한 배율로 다시.
- 쪽 하나가 16 Mpx를 넘는 배율(크게 확대)은 2048 px 칸으로 나눠 **타일이 보이는 칸만** 그림. 화면용 그림은 합계 96 Mpx 안에서 오래된 것부터 버림(LRU),
  pdf.js 동시 2개·최근 요청 먼저.
- 그리는 동안은 이미 있는 가장 선명한 그림을 늘여 보여 주되 타일을 **미완성**으로 표시 → 다 그려지면 그 타일을 다시 그림(G 해결).
- 회전·뒤집힘·비균등 배율 쪽은 예전 경로(변환으로 그림). 내보내기·썸네일·인쇄(`exact`)는 그대로.
- 이미지 레이어(래스터): 100 % 이상 nearest·이하 고품질 축소를 실제 장치 배율(개체 배율 포함)로 판단.
