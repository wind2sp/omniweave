# 글자 인식(OCR) — 1단계: 조사·설계·시제품·측정

2026-11-12 · OCR 부서 · 제품 요구: "오메에서 이미지로 불러온 양식이 있다면 OCR 기능으로 문자 편집이 가능하도록 해 줘. OCR로 이미지를
한글·Word 또는 기타 양식의 텍스트가 살아 있는 문서로 저장되게 해 줘."

**한 줄 요약**: 자체 신경망 실행기(Loom Infer)를 그래프 모델로 넓혀 PP-OCRv5 모바일 검출기 + 한국어 인식기(Apache-2.0)를
**서드파티 런타임 없이** 돌리는 데 성공했다(공식 모델 카드 예시와 글자까지 일치). 그 위에 우리 것인 기울기 보정·띄어쓰기 복원·
괘선 표/체크 상자 재구성·글꼴 크기/굵기 추정·문서 재구성(HWPX/DOCX/PDF, 검색 PDF)을 얹었다. 합성 시험 문서 21쪽에서
한국어 CER clean 2.5% / scan 4.7% / photo 7.8%, 영어 clean 0.9%, 표 구조 100%, 체크 상자 36/36. 속도는 1단계 A4 한 쪽 약 50초
→ 2단계에서 **WebGPU 2.8~4 s, CPU만 9~15 s**(결과 글자 동일) — 3.5장. 배포 크기 결정은 4장.

## 1. 조사 요약 (읽기만 함, GUIDE 15장)

### 1.1 글줄 검출

| 방법 | 핵심 | 장단점 | 출처 |
|---|---|---|---|
| **DB / DBNet** | 글자 영역 확률 지도 + 미분 가능한 이진화. 줄어든(shrink) 영역을 연결 성분으로 뽑고 D = A·r/L 만큼 되돌려 키움 | 후처리가 단순(문턱·연결 성분)하고 가벼움. 문서 글줄에 잘 맞음 | Liao 외, AAAI 2020 [arXiv:1911.08947](https://arxiv.org/abs/1911.08947), DBNet++ [arXiv:2202.10304](https://arxiv.org/abs/2202.10304) |
| CRAFT | 글자 단위 영역 + 글자 사이 연결(affinity) 지도 | 곡선·임의 모양 글자에 강함. 글자 단위 학습 데이터 필요. 공개 가중치의 이용 조건은 코드 라이선스와 따로 확인 필요 | Baek 외, CVPR 2019 [arXiv:1904.01941](https://arxiv.org/abs/1904.01941) |
| EAST | 픽셀마다 회전 사각형 회귀 + NMS | 긴 글줄에서 수용 영역 한계, NMS 필요 | Zhou 외, CVPR 2017 [arXiv:1704.03155](https://arxiv.org/abs/1704.03155) |

### 1.2 글줄 인식

| 방법 | 핵심 | 비고 | 출처 |
|---|---|---|---|
| **CRNN + CTC** | CNN 특징 → 순환/열 단위 시퀀스 → CTC(정렬 없는 학습, 탐욕 복호) | 작고 빠름. 글자 위치(시간 단계)가 그대로 나옴 → 캐럿·띄어쓰기 복원에 씀 | Shi 외 [arXiv:1507.05717](https://arxiv.org/abs/1507.05717), CTC: Graves 외, ICML 2006 |
| **SVTR(-tiny)** | 이미지를 조각으로 나눠 지역·전역 혼합 블록(가벼운 어텐션), CTC 출력 | PP-OCRv3 이후 PaddleOCR 인식기의 목(neck)이 이 계열(EncoderWithSVTR) | Du 외, IJCAI 2022 [arXiv:2205.00159](https://arxiv.org/abs/2205.00159) |
| PARSeq | 순열 언어 모델 + 자기회귀/비자기회귀 복호 | 영어 장면 글자 최고 수준. 한국어 공개 가중치 없음, 복호가 무거움 | Bautista & Atienza, ECCV 2022 [arXiv:2207.06966](https://arxiv.org/abs/2207.06966) |
| PP-OCR(v3~v5) | PP-LCNet(V3) 백본 + SVTR 목 + CTC, 학습 시 보조 머리(NRTR/GTC)는 추론에서 버림 | 모바일용 공개 가중치가 언어별로 있음(한국어 포함) | [PP-OCRv3 arXiv:2206.03001](https://arxiv.org/abs/2206.03001), [PP-LCNet arXiv:2109.15099](https://arxiv.org/abs/2109.15099) |

### 1.3 한국어 고유 문제

- **출력층 크기**: 완성형 음절 11,172자 + 한자·기호·라틴 → PP-OCRv5 한국어 인식기는 11,947 클래스. 분류기 하나가 120×11,947 ≈ 143만
  매개변수(모델 전체 333만의 43%), 실행 시간의 약 10%. **자모 분해 출력**(초성 19 + 중성 21 + 종성 28 = 68개 머리 3개, 유니코드
  3.12장의 조합식 `0xAC00 + (초·21 + 중)·28 + 종`)이면 분류기가 약 1/170로 준다 — 단 우리 모델을 학습할 때만 가능(5장).
- **띄어쓰기**: 한국어 인식기는 띄어쓰기를 자주 빼먹는다(공식 모델 카드 예시도 "자기는돈이", "저는오늘오후에"). 실제 측정(2장):
  우리 인식에서 띄어쓰기 복원을 끄면 CER이 공백 제외 CER의 5~7배(3.2).
- **비슷한 음절**: 았/었, 의/위, 습/슴처럼 자모 하나만 다른 혼동이 대부분. → 1등과 2등 후보가 자모 하나 차이면 "확인할 글자"로 표시.

### 1.4 레이아웃·전처리

- **기울기**: 투영 프로파일(글줄이 수평일 때 행 히스토그램이 가장 날카로움). 0.5° 간격 → 0.05° 세밀 탐색. 사진 왜곡(dewarp)은 2단계.
- **이진화**: Sauvola(지역 평균·표준편차, 적분 영상으로 O(1)) — [Sauvola & Pietikäinen, Pattern Recognition 33(2), 2000].
- **표**: 긴 가로·세로 잉크 줄(괘선) → 교차로 묶은 틀 → 격자선 → 칸. 칸 사이 경계선이 없으면 병합 칸(colSpan/rowSpan).
  괘선 없는 표(공백 정렬)는 2단계.
- **문단·단(column)**: 글줄을 위→아래로 보며 높이·간격·가로 겹침이 맞으면 같은 덩어리, 같은 줄 높이에 이미 줄이 있으면 다른 단/칸.

### 1.5 가중치 후보와 라이선스

| 후보 | 라이선스 | 한국어 | 크기(공식) | 판단 |
|---|---|---|---|---|
| **PP-OCRv5 mobile det + korean_PP-OCRv5_mobile_rec** (PaddlePaddle 공식 HF) | Apache-2.0(모델 카드 메타데이터, PaddleOCR 저장소 LICENSE) | 전용 인식기, 카드 정확도 88.0%(줄 전체가 맞아야 정답) | 4.7 MB + 13.3 MB(fp32) | **채택(시제품)**. GPL-3.0 프로젝트에 Apache-2.0 포함 가능(NOTICE·라이선스 전문 동봉) |
| Tesseract 5 LSTM + kor.traineddata | Apache-2.0 | 있음 | ≈ 15 MB(kor best) | 자체 레이아웃 엔진이 붙어 있고 C++ — 우리 실행기로 옮기기 어려움. 비교 기준선 후보 |
| EasyOCR (CRAFT + CRNN) | 코드 Apache-2.0, CRAFT 가중치 조건 별도 확인 필요 | 있음 | det ≈ 80 MB | 너무 큼, 가중치 조건 불명확 |
| 우리 모델 직접 학습 | 우리 것 | 자모 분해 출력 | 목표 < 3 MB | 5장(2단계 이후) |

내려받은 파일·해시·출처는 `tests/fixtures/ocr/models-manifest.json`. 내려받은 코드는 하나도 실행하지 않았다(그래프 JSON·텐서 파일·
YAML 글자 목록만 읽음). 가중치는 저장소에 넣지 않았다(결정 대기, 6장).

## 2. 설계

```
그림(IMAGE/RASTER) ─ loadSource ─▶ [이미지 작업자] ocr/pipeline.ts
   1 기울기 보정   preprocess.ts  Sauvola → 투영 프로파일 → 회전
   2 글줄 검출     detect.ts      PP-OCRv5 det (Loom Infer 그래프) → DB 후처리(연결 성분, unclip)
   3 글줄 인식     recognize.ts   높이 48로 맞춤 → PP-OCRv5 ko rec → CTC 복호(글자 위치·2등 후보) → 띄어쓰기 복원
   4 레이아웃      layout.ts      괘선 → 표 격자·병합 칸 / 체크 상자 ☐☑ / 문단·정렬·크기·굵기
   5 재구성        reconstruct.ts "편집 가능한 문서"(글상자·표 + 원본 잠금 층) 또는 "텍스트 레이어만"(투명 글자)
   ▶ ui/ocrActions.ts: 한 번의 실행 취소로 삽입(레이어 그룹 "글자 인식 결과")
   ▶ 저장: 기존 내보내기 그대로 — HWPX/DOCX(흐름), PDF(위치 그대로), 투명 글자 → PDF 보이지 않는 글자 층(렌더 모드 3)
```

### 2.1 Loom Infer 그래프 모델 (`src/core/image/infer/graph.ts`, `scripts/convert-ppocr.mjs`)

- 같은 LWT1 그릇, `meta.format = "graph"`: 번호 붙은 값 위의 평평한 연산 목록 + 이름 붙은 가중치(fp16 또는 출력 채널별 int8).
- 변환기(우리 코드, 한 번만 실행): Paddle PIR `inference.json` + `inference.pdiparams`(이름순 저장 — 234개 모두 모양 일치로 확인) +
  `inference.yml`(글자 목록 11,945자). 추론에 필요 없는 것을 접는다: conv 편향 reshape+add, conv 뒤 BatchNorm, PP-LCNetV3의
  학습용 "learnable affine" 스칼라 쌍(conv 또는 활성화 뒤 post-affine으로), dropout/assign. 검출 434→116 연산, 인식 407→137 연산.
- 새 연산: 보폭·그룹(깊이별) conv, 전치 conv(겹치지 않는 k=s 빠른 길), hardswish/hardsigmoid/swish, 적응 평균 풀링, 최근접 확대,
  NumPy 방송 add/mul, matmul(가중치 곱은 1×1 conv로 WASM SIMD 커널 재사용), layer norm, softmax, reshape/transpose/slice/shape/stack.
  1×1·3×3 보폭 1 conv는 기존 WASM SIMD 커널을 **별도 인스턴스**로 씀(U²-Net이 상주시킨 가중치와 안 섞이게).
- **수치 검증**: 공식 모델 카드 예시 줄 그림 → 공개 결과 `리에 씨가 자기는돈이 많이있는다고 했어요`(0.9142).
  우리 fp16: **글자까지 동일, 점수 0.9137**. int8: 띄어쓰기 1개 빠짐(점수 0.918).

### 2.2 우리가 더한 것 (오픈소스 파이프라인보다 나은 점 — 측정 가능)

1. **기하 띄어쓰기 복원**: CTC 시간 단계로 글자 위치를 알고, 줄 그림의 세로 잉크 프로파일에서 이웃 글자 사이 빈칸 폭을 잰다.
   빈칸 ≥ 0.3 em(검출 core 높이로 em 추정)이면 공백 삽입. 0.15·0.2·0.3·0.38 em을 재서 0.3이 가장 좋았다.
   (0.2 em → 0.3 em만으로 보고서 CER 2.35% → 1.76%.) 복원 끔/켬 비교: CER **2.5~3.8배 낮아짐**(3.2).
2. **자모 단위 "확인할 글자"**: 2등 후보가 자모 하나만 다르면(았/었) 노란 표시 + 마우스를 올리면 후보. 재구성 시 형광펜 run.
3. **양식 재구성**: 괘선 표(병합 칸 포함) → TABLE, 체크 상자 → ☐/☑ 글자(체크 여부 판정), 글상자에 크기·굵기·정렬·줄 간격.
4. **문서로 저장**: 재구성 결과는 기존 HWPX/DOCX/PDF 내보내기로 그대로 저장(새 형식 코드 없음). "텍스트 레이어만"은
   그림 위 투명 글자 → PDF에서 보이지 않는 검색 글자 층(pdf.js로 추출 확인: "홍길동", "서울특별시 중구 세종대로 110").
   글자 너비를 자간(Tc)으로 맞추면 PDF 뷰어가 글자 사이를 공백으로 읽어("홍 길 동") 검색이 깨져서, 자간 대신 글자 크기를 줄여 맞춘다.

알려진 문제(1단계 끝): 큰 굵은 제목의 첫 글자가 빠지는 경우가 있었다(보고서 scan "mni 분기 보고서" — 굵은 O가 체크 상자로 오인).
테두리 두께 조건(얇은 선만 상자)으로 고쳤고 그 쪽에서 다시 확인함; 3장 수치는 이 수정 전 측정이라 보고서 계열은 약간 좋아질 수 있다.

## 3. 측정 (합성 시험 문서)

시험 문서: `scripts/ocr-synth.py`가 이 PC 글꼴(맑은 고딕·바탕·굴림·Arial·Times — 그림을 그리는 데만 사용, 배포 안 함)로 그린
A4 150 dpi 7종 — "Omni 분기 보고서"(고딕/바탕, 2단, 수치 표), "오메 신청서"(고딕/굴림, 병합 칸 표, 체크 상자 6개, 서명란),
영문 "Omni Quarterly Notes"(Arial/Times), 회의록(굴림, 숫자·기호·☑ 섞임) — 각각 3가지 상태:
**clean**(깨끗), **scan**(1.2° 기울기, 흐림 0.6, 점 잡음, JPEG 60), **photo**(−2.8°, 흐림 1.0, 잡음, JPEG 45, 고르지 않은 조명).
공개 PD 한국어 스캔은 이번에 넣지 않았다(PD가 분명한 자료를 고르는 데 시간이 들어 2단계로; 실제 그림은 모델 카드 예시 2장으로만 확인).
평가: `scripts/ocr-eval.ts` — 정답 글줄 상자 안에 들어온 인식 글자를 모아 편집 거리로 CER/WER, 표는 (행, 열, 병합)이 같은 칸 비율.

### 3.1 요약 (PP-OCRv5 fp16, 검출 입력 긴 변 1280, 띄어쓰기 복원 0.3 em) — 21쪽

| 묶음 | 쪽 | CER | CER(공백 제외) | WER | 글줄 검출 재현율 |
|---|---|---|---|---|---|
| 한국어·혼합 clean | 5 | **2.46%** | 1.31% | 11.8% | 97.8% |
| 한국어·혼합 scan | 5 | **4.72%** | 1.75% | 26.5% | 98.9% |
| 한국어·혼합 photo | 5 | 7.80% | 4.32% | 38.0% | 97.2% |
| 영어 clean | 2 | **0.91%** | 0.77% | 5.2% | 100% |
| 영어 scan | 2 | 2.48% | 1.35% | 17.5% | 100% |
| 영어 photo | 2 | 18.25% | 16.22% | 46.7% | 86.5% |

- **표 구조**: 표 24개 전부 찾음(24/24), 칸 (행·열·병합) 일치 **100%**(병합 칸 포함), 칸 글자 CER 0~15%(photo가 최악).
- **체크 상자**: 신청서 6쪽 × 6개 = 36개 모두 찾고 체크 여부 **36/36** 맞음.
- **기울기**: 1.2° → 1.2/1.15°, −2.8° → −2.8/−2.75° 추정(오차 ≤ 0.05°).
- **굵게**: 글줄 단위 89~100% 맞음. **글꼴 크기**: 평균 오차 9~37%(보고서 9~13%, 신청서 19~37% — 큰 제목·서명란에서 커짐, 2단계 보정).
- **약점**: photo(흐림 1.0 + JPEG 45, 150 dpi)는 영어 Times에서 CER 22% — 낮은 해상도 사진은 확대 후 인식이 필요(2단계).
  scan의 CER과 공백 제외 CER 차이(4.7 vs 1.8)는 흐린 그림에서 띄어쓰기 복원이 덜 맞기 때문 — 잉크 문턱을 Sauvola로 바꾸는 개선 여지.
- 쪽별 수치: 평가 결과 JSON(저장소 밖, 보고서에 경로).

### 3.2 띄어쓰기 복원 효과 (같은 모델, 복원만 끔/켬)

| 쪽 | 복원 끔 CER / WER | **복원 켬** CER / WER |
|---|---|---|
| report-clean | 6.67% / 40.7% | **1.76% / 7.3%** |
| form-scan | 8.66% / 55.3% | **4.31% / 26.3%** |
| mixed-clean | 9.87% / 57.1% | **3.47% / 22.0%** |

공백 제외 CER은 그대로(0.95%·1.28%·1.71%) — 늘어난 정확도는 전부 띄어쓰기다. 원본 PP-OCR 파이프라인(복원 없음)보다
CER을 2.5~3.8배 낮춘, 측정 가능한 우리 쪽 이점. 공식 모델 카드 예시 출력도 "자기는돈이"처럼 띄어쓰기를 빠뜨린다.

### 3.3 가중치 정밀도

| 조합 | 파일 크기 | report-clean CER | form-scan CER | mixed-clean CER |
|---|---|---|---|---|
| fp16 검출 + fp16 인식 | 2.46 + 6.80 = **9.26 MB** | 1.76% | 4.31% | 3.47% |
| fp16 검출 + int8 인식 | 2.46 + 3.57 = 6.03 MB | 1.76% | 5.05% | 3.47% |
| int8 검출 + int8 인식 | 1.36 + 3.57 = **4.93 MB** | 1.57% | – | – |

int8(출력 채널별 배율)은 이 세트에서 fp16과 차이가 잡음 수준(fp32 원본은 18.0 MB).

### 3.4 속도·메모리 — 1단계 (이 PC, Node, CPU 한 스레드 + WASM SIMD, 다른 작업과 CPU 공유 중). 2단계는 3.5

| 단계 | A4 150 dpi 신청서(글줄 33) |
|---|---|
| 기울기 보정 | 0.1~0.8 s |
| 검출(1280×896 입력) | 8~10 s |
| 인식(줄마다) | 43 s (줄당 ≈ 1.3 s) |
| 레이아웃 | 0.15 s |
| **합계** | **≈ 53 s** · 최대 RSS 194~265 MB |

- 인식 한 줄(폭 800 px 상당)은 약 1.8 GMAC: 1×1 conv 1.5 G(WASM SIMD ≈ 3 GMAC/s), 깊이별 conv 0.1 G(TS라 상대적으로 느림),
  분류기 0.14 G. vitest 작업자 안에서는 같은 반복문이 Node보다 약 2.5배 느려 속도는 번들한 Node로 쟀다.
- **WebGPU는 이번에 재지 못했다**(Browser 창의 dev 서버가 다른 체크아웃 설정으로 떠서 중단·종료). 2단계 첫 일.
- 가속 여지: ① 글줄을 작업자 여러 개에 나눔(줄은 서로 독립 — 8코어면 4~6배), ② WebGPU 그래프 실행기(webgpu.ts 확장;
  1×1 conv·matmul이 대부분), ③ 깊이별 conv WASM SIMD 커널, ④ 검출 입력 1024(재현율 확인 필요). 목표 A4 한 쪽 5초 이하.

### 3.5 속도 2단계 (2026-11-12, 속도 부서)

결과: **WebGPU가 있으면 A4 한 쪽 2.8~4 s**(데워진 뒤), WebGPU 없이 CPU만이면 Node 한 스레드 15 s / 작업자 4~6개 9~10 s
(1단계 53~60 s). **정확도 그대로**: 합성 21쪽 모두 CPU 결과의 오류 목록이 1단계와 글자까지 같고(CER 평균 5.018% → 5.018%),
WebGPU 결과의 글줄 글자도 21쪽 모두 CPU와 같다. 이 PC(Core Ultra 5 125H, Arc 내장 GPU)는 다른 작업이 CPU 30~60%·GPU를
쓰고 있어 시간은 ±2배 흔들린다 — 표는 같은 조건에서 잰 대표값.

| 기법 (A4 신청서 150 dpi, 글줄 33) | 검출 | 인식(33줄) | 합계 |
|---|---|---|---|
| 1단계 (Node 한 스레드) | 20.5 s | 39.3 s | 60 s |
| WASM conv 반복 순서 행→8픽셀→채널묶음(입력 블록이 L1에 남음, 비트 동일) + convT 행 순서 | 9.8 s | 줄당 1.4→1.0 s | – |
| 깊이별 k3/k5·보폭 2 WASM 커널, 1×1을 한 줄로(복사 1번), 3×3 보폭 2(열 짝/홀 분리) | 6~8 s | – | – |
| **1e-20 미만 가중치 0으로**(int8 죽은 채널 배율 1e-40 → 비정규 수 곱마다 x86 마이크로코드 보조: 1×1 conv 하나 20~40배 느렸음) | 4.2 s | 줄당 0.8 s | – |
| convT를 1×1 GEMM + depth-to-space로, 1×3 conv는 im2col, (2,1)·(1,2) 보폭 깊이별 | 3.1 s | 11.9 s | **15.3 s** |
| + 인식 작업자 4 / 6개 (Node worker_threads, 메시지 전달·transferable) | 3.5~4.4 s | 4.8~5.5 s | **9.1~9.9 s** |
| **WebGPU** (Browser 창, 이미지 작업자, 데워진 뒤 · 최고 / 보통) | 0.8 / 0.7~1.4 s | 1.1 / 1.4~2.8 s | **2.8 / 3.1~4.2 s** |

- **WebGPU 그래프 실행기** `infer/graphGpu.ts`: graph.ts와 같은 연산 목록을 GPU에서. 실수 텐서는 GPU 버퍼, 모양·정수 텐서는 CPU에서
  graph.ts의 `evalNode`로 계산(모양이 기록 중에 다 정해짐). 한 번 실행 = 연산마다 dispatch 하나, 매개변수는 저장 버퍼 하나에 256바이트
  간격, 출력만 읽어 옴. 커널: 조밀 conv(출력 4채널×4픽셀 레지스터 타일), 그룹/깊이별 conv, convT, 방송 산술, 활성화, 평균 풀링,
  최근접 확대, 보폭 복사(전치·자르기·이어붙이기), matmul(4행 타일), layer norm, softmax(작업그룹 리덕션). 검출 1536 입력 CPU 대비
  최대 오차 6.7e-5(문턱 0.3 뒤집힘 0개), 인식 7.7e-6.
- **이미지 작업자의 가속 선택** (`worker.ts ocrAccel`): WebGPU가 있으면 검출 + 글줄(3줄 동시 — 하나를 기록하는 동안 GPU가 나머지를 실행)
  을 GPU로, CPU 작업자는 띄우지 않는다(작업자 하나 ≈ 100 MB). 없거나 한 번 실패하면 CPU 풀(`ocr/recPool.ts`: 코어−2, 최대 6,
  deviceMemory/2 이하, 긴 줄부터, 줄 결과는 순서대로). GPU 실패·장치 분실은 그 쪽만 CPU로 다시 하고 다음 쪽부터 CPU.
- **첫 사용**: GPU 준비(셰이더 컴파일 병렬 + 첫 큰 버퍼를 드라이버가 커밋)가 이 PC에서 8~15 s. 대화상자가 열릴 때 `warmOcr`가 모델 적재와
  가장 큰 입력(1536², 폭 3200)으로 한 번씩 돌려 미리 치른다. 버퍼는 2의 거듭제곱 크기 풀에서 재사용, 명령은 8 dispatch마다 제출
  (Windows TDR 2 s 회피 — 첫 실행에서 장치 분실이 났었음).
- **고친 결함**: 이미지 작업자에서 모델 주소가 작업자 스크립트 기준으로 풀려(`src/core/image/models/ocr/…`, 빌드에서는 `assets/models/…`)
  앱의 OCR이 "LWT1 model expected"로 실패했다 → 요청에 페이지 base URL을 실어 보낸다(`setModelBase`).
- **안 한 것/한계**: 줄 묶음(batch) 실행 — 그래프가 batch 1이고, 같은 폭으로 패딩하면 계산이 늘어 이득이 없음(작업자·GPU 동시 실행으로
  대신). int8 dot 경로(i32x4.dot_i16x8)·relaxed SIMD FMA — 활성값 양자화/반올림이 달라져 "같은 결과"를 깨므로 보류. 검출 해상도 낮추기·
  영역만 재검출 — 재현율 영향 측정 필요(보류). CPU만으로는 검출(3 s)이 한 스레드라 5 s 목표 미달 — 검출을 작업자에 나누려면 연산마다
  텐서를 주고받아야 해(SharedArrayBuffer 없음) 다음 일. 메모리: Node 한 스레드 최대 RSS 264~275 MB(1단계 249~301), 작업자 4개 683~869 MB,
  GPU 경로는 GPU 버퍼 풀 ≈ 380 MB(검출) + 130 MB(인식).
- 시험: `tests/ocr/ocr.test.ts` WASM 커널 비트 일치(조밀·깊이별·보폭·1×3, f32 기준과 합산 순서까지 같은 참조), convT TS·WASM 정확 일치,
  `tests/ocr/recPool.test.ts` 풀 순서·실패·크기. GPU 셰이더는 Node에 WebGPU가 없어 Browser 창에서 CPU와 맞춰 봄(위 수치).
- 측정 도구: `scripts/ocr-eval.ts --workers N`(앱과 같은 recPool을 worker_threads로).

## 5. 우리 모델(2단계 이후)

- 같은 구조(PP-LCNetV3 계열 + 가벼운 어텐션 + CTC)를 우리 코드로 정의하고 **자모 3머리 출력**(68클래스)으로 학습:
  분류기 143만 → 약 8천 매개변수, 모델 ≈ 3.4 MB(fp16) 목표, 출력이 조합식이라 없는 음절도 표현.
- 데이터: OFL 한글 글꼴(본고딕/나눔 등 — 렌더한 그림을 학습에 쓰는 것은 OFL이 막지 않는 것으로 보이나 확인 필요)로 합성 렌더 +
  공공누리 1유형/PD 스캔(출처 표기 조건 확인). 학습은 GPU 필요 — 이 PC 밖 자원(비용) 결정 필요.
- 경쟁력 지표: 같은 시험 세트에서 CER, 모델 크기, 쪽당 시간 — PP-OCRv5 한국어(이번 측정치)를 기준선으로.

## 6. 권장과 다음 단계

**권장: A(int8 묶어 배포) + 2단계 속도 작업**, 일·중 등 추가 언어는 C(필요할 때 내려받기). 이유: 4.9 MB로 앱이 크게 늘지 않고,
그림을 열면 인터넷 없이 바로 인식된다("그림은 밖으로 나가지 않는다"는 약속과 맞음). D는 A를 기준선으로 두고 나중에 대체.

다음 단계(제안 순서):
1. ~~**속도**: 글줄 병렬(작업자 풀) → WebGPU 그래프 실행기 → 깊이별 conv WASM~~ — 2단계에서 함(3.5). 남은 것: CPU만일 때 검출 병렬,
   GPU 첫 사용 준비 시간 줄이기.
2. **앱 확인**: 대화상자를 실제 앱에서 실행·스크린샷(이번엔 dev 서버 문제로 못 함), 진행률 표시(onProgress 있음).
3. **재구성 품질**: HWPX/DOCX는 지금 흐름 순서(위→아래)로만 저장 — 2단·글상자 위치를 살리려면 HWPX 글상자/DOCX 텍스트 상자
   내보내기가 필요(Office Surgeon 부서와 협의). 글꼴 크기 보정, 괘선 없는 표, 사진 왜곡 보정, 세로쓰기.
4. **실제 문서 평가**: PD·공공누리 1유형 한국어 스캔 세트(매니페스트·라이선스 기록, 저장소에 그림 두지 않음).
5. **스캔 PDF 바로 처리**: PDF Surgeon이 스캔 쪽에 글자 층을 증분 추가(ENGINE_RESEARCH A4).
6. (선택) 우리 모델 학습(5장).
